# ADR-001: Capas simples para la persistencia; la notificación ya tiene su punto de extensión

## Estado

Aceptado. 12 de noviembre de 2026.

## Contexto

El sistema de reembolsos ya integra tres patrones: Chain of Responsibility para validar, Strategy para calcular y Observer para notificar. Ahora hay que decidir si conviene migrar a arquitectura Hexagonal completa, con puertos e interfaces intermedias para cada dependencia externa, o mantenerlo en capas simples.

La guía de la unidad da el criterio: Hexagonal vale la pena en sistemas que van a vivir tres años o más **con cambios de infraestructura**. Este ADR responde ese criterio con los datos del proyecto, por separado para cada dependencia externa:

| Dependencia | Qué tiene hoy el proyecto | ¿Hay un cambio de infraestructura conocido? |
|---|---|---|
| Persistencia | Un repositorio (`RepositorioSolicitudesJpa`) que usa un solo servicio, con una consulta derivada (`findByEmpleadoIdAndEstado`) y dos operaciones heredadas (`save` y `findById`). Base de datos H2. | **No.** No hay ningún plan de cambiar el motor de base de datos. |
| Notificación | El servicio avisa a una `List<ObservadorCambioEstado>` y no conoce a ningún notificador concreto. | **Sí.** Contabilidad anunció para el próximo trimestre una integración por API externa para pagar las solicitudes aprobadas. |

El sistema reemplaza una hoja de cálculo y es probable que viva varios años. Pero la duración sola no basta: el criterio pide además cambios de infraestructura, y eso solo se cumple para la notificación.

## Alternativas consideradas

1. **Hexagonal completa.** Un puerto `RepositorioSolicitudes` en el núcleo, un adaptador JPA en `infraestructura`, y un puerto explícito para la notificación.
2. **Capas simples en todo.** El servicio depende directamente del repositorio JPA y de la interfaz de observadores que ya existe.
3. **Mixta.** Puerto solo donde hay un cambio conocido. Es lo que se decide, aunque en la práctica coincide con la alternativa 2, porque la notificación ya tiene su puerto.

## Decisión

**Persistencia: se mantienen las capas simples.** `SolicitudReembolsoService` sigue dependiendo directamente de `RepositorioSolicitudesJpa`. Un puerto de persistencia hoy sería una interfaz con exactamente los mismos tres métodos que ya da Spring Data, más un adaptador que solo delega en él. Es una abstracción especulativa (YAGNI) que no tiene ningún caso de uso que la pida.

**Notificación: no se cambia nada.** `ObservadorCambioEstado` ya cumple el papel de un puerto: el servicio solo conoce la interfaz. Cuando llegue la API de Contabilidad, su implementación se agrega como **una clase nueva en `infraestructura`** que implementa `ObservadorCambioEstado` y llama a la API, y reemplaza a `NotificadorContabilidad`. No va dentro de `procesamiento.notificacion`: un cliente HTTP es infraestructura, y la Regla 1 de ArchUnit impide que `procesamiento` dependa de `infraestructura`. Así el cambio no toca `SolicitudReembolsoService` ni a los otros dos observadores.

## Consecuencias

**Positivas**

- No se agregan interfaces, adaptadores ni conversiones de persistencia sin un caso de uso real.
- El único cambio de infraestructura con fecha conocida ya tiene su punto de extensión, y las reglas de ArchUnit dicen dónde debe vivir la implementación nueva.
- Hay menos clases que leer: quien llega al proyecto ve de una vez que el servicio guarda con Spring Data.

**Negativas**

- Si algún día se cambia de motor de base de datos o se agrega otra fuente de datos, el puerto de persistencia habrá que introducirlo después y tocar el servicio. Se acepta esa deuda técnica de forma consciente, porque hoy no hay ninguna señal de ese cambio.
- Las pruebas unitarias del servicio dependen de la interfaz de Spring Data. Por eso se doblan con un mock de Mockito y no con un fake escrito a mano, que tendría que implementar decenas de métodos.
- Un revisor que espere simetría total (puertos en todas las dependencias) puede leer la asimetría como una inconsistencia si no lee este ADR.
- Cuando se integre la API de Contabilidad habrá que decidir qué pasa si la llamada falla. Hoy los observadores corren después de guardar, dentro de la misma petición, así que un error de la API llegaría al cliente aunque el cambio de estado ya esté guardado. Ese manejo se decide cuando exista la API, no antes.

## Señales para revisar esta decisión

- Aparece un segundo mecanismo de persistencia o un plan concreto de cambiar de motor de base de datos.
- El servicio necesita consultas que Spring Data no expresa bien y empiezan a mezclarse detalles de JPA en la lógica de aplicación.
